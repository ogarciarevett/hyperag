# Transactional lexical source fence

PostgreSQL remains authoritative. This migration installs the consistency foundation for a future in-process lexical index; it does not enable an index, worker, rebuild or retrieval setting. Existing lexical scoring remains unchanged. Both Rust and TypeScript migrators install the fence; it is independent of the optional SQL statistics/postings cache.

The singleton `lexical_index_state` carries a stable logical database UUID, committed epoch, random fence token and retention floor. The first source mutation in a transaction advances the epoch and random token once. Changed memory/version IDs and authorization/reset markers are coalesced into ID-only events at that epoch. All events for one epoch share its predecessor and fence token. Rollback undoes source, counter and event together. Source IDs have no foreign key to memories, so deletion cannot erase its own event. Authorization changes have no memory ID; truncation emits an explicit reset marker requiring rebuild. No source text, prompt or credential is copied into the outbox.

Writers, migration and retention use the existing advisory transaction lock `(1213811052,1)`. Store writers acquire it before row/table locks; statement triggers also cover direct DML. Administrative source-write transactions must take that advisory lock before their first table/row lock, including direct DML, `FOR UPDATE` and `TRUNCATE`. Transactional counters, rather than sequences, keep committed transaction epochs contiguous after rollback.

Consumers must read the fence, grants, events and final source rows in one repeatable-read snapshot, coalesce IDs, and validate the full event/token chain through that snapshot's final epoch. Publish only after an index commit and reader reload. The checkpoint is `(database_id, epoch, fence_token)`, not just an epoch: a divergent restore/clone can reach the same counter with different source contents. Each epoch links the preceding committed token to its new random token; validate the chain per epoch, including all its changed IDs/markers. A mismatched lineage, gap, lag, incompatible manifest or reset requires SQL fallback/rebuild; no stale top-k response is permitted.

Retention is explicit: `SELECT lexical_index_prune(E)` takes the same guard, rejects null/negative/future boundaries, deletes events through E and monotonically records the floor without changing source identity, epoch or token. Readers behind that floor must rebuild. Retention refuses to run after source writes in the same transaction. No pruning scheduler or automatic retention is introduced here.

Cost: one state-row update per source transaction and one ID/token event per distinct changed memory ID or marker in that transaction, plus unique-index entries and WAL. Repeated IDs coalesce even across source statements. Retention is unbounded until explicitly pruned. Disk/WAL/write-latency cost has not been measured on live data; measure under the shared resource gate before rollout. This slice adds no model load, search thread or background process.
