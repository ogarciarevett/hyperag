# Rust lexical scorer comparison and rollback

`HYPERAG_LEXICAL_SCORER=bm25|fast|indexed-bm25` selects the Rust lexical scorer. Unset defaults to the original corpus BM25. Set the environment value and restart the service to compare or roll back without a rebuild. Unknown values fail initialization. The public `bm25` channel selector and TypeScript scorer remain compatible; all Rust paths use the same scope/current-version/deletion/status/valid-time predicates before a candidate budget.

The opt-in fast path expands the query into distinct lexemes, drops English stopwords, and retrieves up to `candidatesPerChannel` authorized current candidates per lexeme with the stored tsvector's GIN-indexed `@@` predicate and `ts_rank_cd`. It unions those bounded candidates and prioritizes best per-term rank, matched-term count, then reciprocal-rank contribution. For queries with no more distinct non-stopword lexemes than the candidate budget, each term's best document survives the final budget. This protects rare-term matches from repeated common-term documents without global document-frequency statistics. Larger query vocabularies remain bounded by the final budget and do not have that coverage guarantee.

The authorization `EXISTS` semijoin must precede each per-term limit because scopes and the current-version pointer live on the memory identity. Denied, historical and invalid rows cannot consume the budget. Only bounded candidate ids/scores go to payload loading and graph expansion. Document lexemes are not unnested; only the small query vector is unpacked once.

Synthetic tests execute the shipped Rust SQL with default planner settings after normal post-bulk `VACUUM ANALYZE`. They assert the GIN Bitmap Index Scan, preserved fixture order and isolation. A separate 100,000-background-row case has one `quartz` document and 24 documents repeating `ordinary` 20 times: fast must retain `quartz` inside its 24-candidate budget, while rollback BM25 must rank it first. Broad terms can still require scanning/ranking many indexed matches; emitted-candidate limits do not bound every authorization or rank computation. Live quality and latency acceptance remains a separate post-merge trial.

`indexed-bm25` uses maintained scoped postings and copied current-document metadata from migrations 0004/0005. The term index selects matching readable scopes before metadata checks; current version, status and valid-time filters stay in `lexical_documents`. Ready queries never access source `memories`/`memory_versions`, unpack document vectors or carry TF JSON through the ranking sort. Only query terms are unpacked. The formula and score/time/id order remain the legacy BM25 definition; the default remains `bm25`.

Both readiness markers and scoring share one SQL statement snapshot. Missing/false/reset readiness selects the untouched legacy query. Complete the two bounded backfills before measuring indexed performance. Copied metadata, posting rows/indexes and serialized write maintenance are its cost; this PR makes no live latency claim.
