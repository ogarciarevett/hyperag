# Maintained lexical statistics (Rust storage)

Migration 0004 adds derived current-document TF/length, corpus counts/length sums, and document frequencies. TF uses stored tsvector positions and length counts unique lexemes, matching the existing BM25 implementation. Counts are keyed by scope and normalized valid-time interval; future consumers must filter readable scopes and the requested valid time. Source memories, versions, models and the default scorer are unchanged.

Source writes update the cache transactionally, including status/current-version changes, scope/validity edits and deletion. Store write transactions take advisory transaction lock `(1213811052,1)` immediately after BEGIN, before any row/table lock; the source statement triggers and backfill take the same lock. This includes corrections, grant changes, invalidation, vectors/settings and DDL. Portable import takes it before its importer lock; All TypeScript writes, including migration, space creation, invalidation and vector insertion, use the guarded transaction helper with the same order. Read-only vector/export transactions take no writer lock. Reads use MVCC and take no writer lock. This trades write concurrency for consistent derived counters; measure write cost before adopting it for a busy writer workload.

Existing data is not scanned or backfilled automatically at startup. Call `SELECT lexical_cache_backfill(64)` repeatedly until it returns zero, using one gated batch at a time. Accepted batch sizes are non-null integers 1–256. New writes are tracked during backfill; `settings.lexical_cache_ready` becomes `true` only when current-row coverage is complete. Empty new databases start ready. Reapplying the migration and refreshing a cached document are idempotent.

Administrative SQL must use `BEGIN; SELECT pg_advisory_xact_lock(1213811052,1);` **before any source access**, then `TRUNCATE` and `COMMIT`. PostgreSQL takes table locks before firing statement triggers; an unguarded concurrent TRUNCATE or SELECT FOR UPDATE cannot be made safe by a trigger. Migrations also acquire the advisory lock before DDL.

Administrative TRUNCATE marks the cache `reset`; the next explicit backfill resets derived tables and rebuilds them. Until readiness is true, a consuming indexed scorer must fall back to legacy scoring and check readiness in the same snapshot as its scoring query. This PR supplies storage only; indexed scoring and stage timing are separate work units.

Migration 0005 adds copied current-version/status/recorded-time metadata and scoped `(lexeme, scope, posting_id)` postings with TF. Numeric keys keep the term index narrow; they are internal and stable while a cached document exists. Guarded source writers maintain metadata, posting TF/scope changes and deletion in the same transaction as the original counters. Metadata-only changes avoid rebuilding unchanged postings. Source text is not copied into the posting table.

After `lexical_cache_backfill` completes, run bounded `SELECT lexical_postings_backfill(64)` batches until zero. Existing rows are upgraded in batches; there is no startup postings population. Both readiness markers must be true in the scoring statement snapshot; otherwise indexed retrieval falls back to legacy. Source TRUNCATE/reset uses the original bounded cache reset/backfill, cascading to postings, then the postings readiness check. Do not truncate derived tables independently without resetting/rebuilding the cache. Additional disk/index space and write amplification must be measured after merge under resource gates.
